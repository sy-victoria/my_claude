# M3：权限系统

日期：2026-07-12

## 做了什么

把"工具执行前要不要问用户"从工具内部（M2 的 bash 确认钩子）抽出来，做成统一的守门人层 `permissions.py`。现在所有工具执行前都经过 `PermissionManager.check()`，工具本身只声明自己的危险级别。

新增/修改文件：
- `minicode/permissions.py`：`decide()` 纯函数决策矩阵 + `PermissionManager`（询问、会话白名单）
- `minicode/tools/base.py`：`Tool` 增加 `permission_level` 字段（read/write/execute，默认 read）
- `minicode/tools/edit_file.py`：声明 `write`；`minicode/tools/bash.py`：声明 `execute`，**删除** M2 的 `ask_user_confirmation` 脚手架
- `minicode/agent.py`：`_execute_tool` 里统一调 `permissions.check()`，拒绝理由作为 tool_result 返回
- `minicode/cli.py`：`--mode default|accept-edits|yolo`，yolo 启动时警告
- `tests/test_permissions.py`：17 个测试；`tests/test_bash.py` 重写（确认相关用例移走）

## 关键设计决策

**1. 策略与机制分离——这是本里程碑的核心思想。**
M2 时 bash 自己实现确认逻辑，看起来能用，但每加一个危险工具就要重复实现一遍，而且"哪些工具要确认"的规则散落在各个工具文件里，改一次策略要动 N 个文件。M3 的做法：工具只**声明**（`permission_level="execute"`），守门人统一**决策**（`decide()`）。以后 M5 加 `write_file`、M7 加 `task`，都只需要声明一个字段就自动获得正确的权限行为。这是 Claude Code 权限模型的骨架，也是通用的架构模式（对应操作系统里的"策略与机制分离"原则）。

**2. `decide()` 做成纯函数，`PermissionManager` 只管交互和状态。**
决策矩阵（3 模式 × 3 级别）是纯逻辑，抽成 `decide(mode, level, in_allowlist) -> "allow"|"ask"`，测试可以直接参数化枚举全部 9 种组合，不需要 mock 任何交互。询问用户、记白名单这些有副作用的部分留在 manager 里。**能变成纯函数的逻辑就变成纯函数**——测试成本的差距是数量级的。

**3. deny 只来自用户按 n，`decide()` 本身不产生 deny。**
真实 Claude Code 有配置规则产生的硬 deny（permission rules 的 deny 列表），我们简化掉了：黑名单命令的拒绝留在 bash 工具内部（那是工具自己的输入校验，不是权限策略），权限层的拒绝只有一个来源——用户的现场决定。简化的理由：学习价值集中在"allow/ask/deny 三态 + 分层决策"这个骨架上，规则语法是纯粹的工程量。

**4. 会话白名单以工具名为粒度。**
按 `a` 之后整个工具（如 bash）本会话免询问。Claude Code 的真实粒度更细（例如 `Bash(git *)` 这种命令前缀规则），我们用工具名粒度表达同一个概念。粒度差异记录在案。

## 踩坑记录

本里程碑没有踩到真正的坑，但有一个值得记录的"意外之喜"（第三次验证"错误信息即 prompt"）：验收场景 4 里，bash 调用被用户拒绝后，模型收到拒绝理由（"请不要原样重试；可以……改用其他方式完成任务"），它**立刻改用只读的 `list_files` 工具**完成了同样的目标（列目录）——而 read 级工具在 default 模式下免询问，所以这次它畅通无阻。整条链路（execute 被拒 → 降级到 read 替代方案 → 完成任务）完全是模型基于拒绝文案自主推理出来的，我们没有写任何"被拒后请尝试其他工具"的分支代码。

这里有个值得思考的安全问题：模型会"绕过"拒绝去达成目标，这次的绕法（用更低权限的工具）是良性的，但设计权限系统时要意识到——**拒绝一个工具不等于拒绝一个意图**。真实产品里这是 alignment 层面要处理的课题。

## 验收结果

单元测试：`uv run pytest` 42 个全绿（新增 17 个权限测试，重写 8 个 bash 测试）。

真实 API 验收（DeepSeek，default 模式，脚本注入询问钩子记录询问次数）：
- ✅ 「读一下 readme.md」→ `read_file` 执行，询问次数 0（read 级免询问）
- ✅ 「创建 demo.txt」→ `edit_file` 触发询问，回答 `a` 后执行成功，文件真实存在
- ✅ 「再创建 demo2.txt」→ 白名单生效，询问次数 0，文件真实存在
- ✅ 「用 bash 的 ls 看看目录」回答 `n` → bash 未执行，模型收到拒绝理由后改用 `list_files` 完成任务（见踩坑记录的分析）

## 跟着学

1. `minicode/permissions.py` 的 `decide()` —— 9 行代码的决策矩阵，对照 `tests/test_permissions.py` 顶部那张 `MATRIX` 参数化表格看，体会"纯函数 + 参数化测试"这对组合的威力。
2. `minicode/agent.py` 的 `_execute_tool()` —— 现在它的结构是：查找工具 → 权限检查 → 执行并捕获异常。三步各自只有几行，这就是 agent 循环里"工具调度"的完整形态（Claude Code 在每一步上更精细，但骨架相同）。
3. 对比 git 历史里 M2 版本的 `bash.py`（`git show 1bac244:minicode/tools/bash.py`）和现在的版本 —— 亲眼看看"临时脚手架被正式系统取代"时代码是怎么变干净的：删掉了确认钩子，只多了一行 `permission_level="execute"`。
