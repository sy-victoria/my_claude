# M5：搜索与精确编辑工具箱

日期：2026-07-13

## 做了什么

补齐在真实代码库干活的工具箱：`glob`（按文件名找）、`grep`（按内容找）、`write_file`（整文件写入），并在 agent 层落地"编辑前必须先读"的硬约束。工具总数达到 7 个。

新增/修改：`minicode/tools/glob_files.py`、`grep_files.py`、`write_file.py`、`tools/__init__.py`（注册）、`agent.py`（`_read_files` 集合 + edit 前检查）、`prompts.py`（工具选择指引更新）、`tests/test_search_tools.py`（11 个测试）。

## 关键设计决策

**1. 工具箱的"正交性"：每个工具回答一类问题，description 里互相指路。**
glob 答"叫这个名字的文件在哪"、grep 答"这段内容出现在哪"、read 答"这个文件里是什么"、list 答"这层目录有什么"。每个工具的 description 都写明"什么时候用我、什么时候用别人"（如 grep 的 description 直接写了"重命名前先用我找定义和引用"）。验收里模型第一步就精准选了 grep，这不是运气，是 description 指路的结果。

**2. "编辑前必须先读"放在 agent 层，不在工具里。**
这条约束需要跨工具的会话状态（哪些文件被读过），而工具是无状态的纯函数，所以状态（`_read_files` 集合）由 Agent 持有，检查在 `_execute_tool` 里做。另一个细节：检查放在权限询问**之前**——注定失败的调用没必要打扰用户确认。M1 时模型是"自发"先读再改的，现在这变成了机制保证（Claude Code 的同款硬约束）。

**3. 搜索工具统一过滤噪音目录并限制结果数。**
`.git`、`.venv`、`__pycache__`、`node_modules` 里的匹配几乎永远是噪音；结果超过 50 条时截断并提示模型缩小范围。这两条都是在保护上下文窗口——M6 的主题在工具层已经开始了。

## 踩坑记录

新的读后编辑约束让 M3 的两个旧测试失败了（它们直接 edit 已存在文件）。修复方式是在测试里预置已读状态，而不是给约束开后门。**新约束打破旧测试是好信号**——说明约束真的在起作用；这时候该改的是测试的前置条件，不是产品逻辑。

## 验收结果

- ✅ `uv run pytest` 56 个全绿
- ✅ 真实 API 验收（21 个文件的合成项目）：「把 calc_total 重命名为 compute_total，所有引用一起改」→ 模型走了 grep（找到 4 文件 6 处）→ read × 4 → edit × 7 → **自发用 bash 跑 pytest 验证**的完整流程；`grep -rn calc_total` 零残留，4 个源文件全部正确更新
- ✅ 未读文件直接 edit 被拒绝并纠正（单测 `test_edit_without_prior_read_is_rejected` 覆盖）

3. 验收日志里模型最后自发跑 pytest 的那一步——这是 M4 system prompt"改完验证"指令和 M2 bash 工具的组合效果，单独看任何一个里程碑都解释不了这个行为。

## 遗留问题

- grep 是纯 Python 逐行扫描，大仓库会慢（Claude Code 用 ripgrep）。学习项目可接受。
- write_file 对已存在文件没有"先读"约束（roadmap 只要求 edit_file）；整文件覆盖的误伤风险比局部替换高，记录在案，M9 若有余力可补。
