# 终端 UI 打磨（M9 之后的补充迭代，非 roadmap 里程碑）

日期：2026-07-13

> 说明：M0~M9 全部完成后，项目所有者继续提了几轮"让它更像 Claude Code"的体验需求。
> 这些改动不对应 roadmap 里的任何一个里程碑，所以没有编号、没有勾选框，但按同样的
> 规格写一篇 devlog——过程里的设计决策跟正式里程碑一样值得记录。

## 做了什么

四轮迭代，逐步把终端体验往 Claude Code 的方向靠：

1. **配色 + 小宠物 + 模型可见性**：`rich.Theme` 换成 DeepSeek 品牌蓝（不是 Anthropic 的橙色——诚实反映"这是谁的模型在跑"）；鲸鱼 🐳 作为吉祥物出现在启动横幅和输入提示符里；启动横幅从两行 `print` 改成 `rich.Panel` 圆角边框（仿 Claude Code 的 welcome box）；输入提示符 `🐳 (sonnet) >` 实时显示当前档位。
2. **`/model` 交互式选择菜单**：不带参数时弹编号列表，回车选号切换，而不是甩一句"用法：..."。
3. **把这个模式推广到 `/mode`、`/plan`，并新增 `/resume`**：三个命令共用同一个菜单渲染函数；`/resume` 让用户在对话中途也能挑一个历史会话恢复（原来只有启动参数 `--resume`）。
4. **工具调用展示改成 `⏺`/`⎿` 格式，`edit_file` 画彩色 diff**：新增 `Agent.on_tool_result` 回调，工具执行完（无论成功/拒绝/报错）都会触发一次。

新增/修改：`minicode/cli.py`（198 行 → 417 行，见"遗留问题"）、`minicode/agent.py`（新增 `on_tool_result` 回调，`_execute_tool` 拆出 `_run_tool` 单一出口）、`minicode/session.py`（新增 `list_sessions`/`load`/`preview`，`load_latest` 改为基于它们实现）。没有新增第三方依赖——全程只用了已经在允许清单里的 `rich`（外加标准库 `difflib`）。

## 关键设计决策

**1. 配色跟着后端走，不硬抄 Anthropic 的橙色。**
这个项目走的是 DeepSeek 的兼容端点，用 Anthropic 的品牌色反而是在冒充。选 DeepSeek 的品牌蓝（`#4D6BFE`）、吉祥物选鲸鱼（DeepSeek 的品牌形象），是"UI 要诚实反映技术栈"这条朴素原则，不是随便选好看的颜色。

**2. 交互菜单和纯函数分发器分层，不是塞进 `handle_slash`。**
`handle_slash(command, agent) -> str` 从 M8 开始就是纯函数（输入字符串、输出文本、不做 I/O），这样测试可以直接断言返回值。给 `/model` 加交互菜单时，没有让 `handle_slash` 自己读键盘——而是在 `cli.py` 主循环里加了一层：先判断"是不是要弹菜单"，弹完菜单拼出完整命令字符串（如 `/model opus`），再调用 `handle_slash`。**决定权在调用方，纯逻辑和 I/O 物理分开**——这样 `handle_slash` 的所有旧测试一个字都不用改，新加的交互逻辑也不需要 mock 键盘输入（本项目里没这么做，但换个场景想验证交互逻辑本身，也不用改动被测的纯函数）。

`_prompt_from_list(options, current, question)` 是三个命令（`/model` `/mode` `/plan`）共用的菜单渲染函数——它们的差异只是"有哪些选项、每项怎么解释"，选择和渲染的机制是一样的，抽出来是消除重复，不是为了显得高级。

**3. `on_tool_result` 回调带 `tool_input`，不止带结果文本。**
一开始设计是 `on_tool_result(name, result)`，但 `edit_file` 要画 diff 需要 `old_str`/`new_str`——工具的返回值只有一句"已修改 xxx"，不包含改动内容。与其为了拿到 diff 再重新读一次文件（多一次 I/O、还可能读到别的进程改过的新内容），不如直接把 `tool_input` 也传给回调——调用方要什么自己从参数里取，Agent 不用关心"CLI 到底想怎么展示"。这是"把展示逻辑完全推给调用方，Agent 只负责给全信息"的分层原则。

**4. `_execute_tool` 拆出 `_run_tool`，让结果回调只有一个触发点。**
原来的 `_execute_tool` 有五个 `return`（未知工具、读后编辑校验、权限拒绝、hook 阻止、正常结果/异常），如果要在每条 `return` 前都补一句"触发回调"，会有五处重复代码，还容易漏改。拆成 `_run_tool`（只负责产生结果文本）+ `_execute_tool`（调用 `_run_tool`，然后统一触发一次 `on_tool_call` 和一次 `on_tool_result`）之后，无论走哪条分支，回调都只在一个地方触发。

**5. `/resume` 复用了 M8 就有的会话文件，没有新建存储层。**
`session.py` 原来只有 `load_latest()`（按文件名排序取最后一个）。给它拆成 `list_sessions(limit)`（列出最近 N 个，新到旧）+ `load(path)`（读某一个）+ `preview(path)`（摘第一句用户消息做列表预览），`load_latest()` 改成基于这两个函数实现（`list_sessions(limit=1)[0]` 再 `load`）。会话文件本来就是按时间戳命名的 JSON，`/resume` 需要的"列出全部、挑一个加载"能力其实一直都在，只是没有暴露成函数。

## 踩坑记录

无实质性踩坑，但有一处需要如实记录的**已知偏差**：`cli.py` 从 198 行涨到 417 行，超过了 CLAUDE.md 3.1 节"单文件不超过 ~300 行，超了就说明职责该拆分了"的规定。目前它同时承担了：参数解析与主循环、slash 命令分发、三个交互式菜单、工具调用/结果的终端渲染（含 diff）、goal 模式。这几块职责边界其实已经很清楚，适合拆成 `cli.py`（入口 + 主循环）+ `display.py`（`_print_tool_call`/`_print_tool_result`/`_print_edit_diff`/主题/mascot 常量）+ `slash.py`（`handle_slash` + 三个 `prompt_*_choice`）。**这轮没有做这个拆分**，因为项目所有者这次要的是"文档记录改动"，拆分是新的结构性改动，按 CLAUDE.md 的精神应该先问过再动手——已经在下面提出，等确认。

## 验收结果

- ✅ `uv run pytest` 100 个全绿（未新增/删除测试用例，纯 UI 改动，行为等价性靠现有测试覆盖 + 手工验证）
- ✅ 启动横幅：真实跑 `uv run minicode`，圆角边框 + 鲸鱼 + "欢迎使用 minicode！" 正确渲染，cwd/档位/权限信息齐全
- ✅ `/model` `/mode` `/plan` 交互菜单：管道输入模拟按键（如 `/mode\n2\n`），菜单正确列出选项、标出当前项、选号后正确切换并回显确认文案
- ✅ `/resume`：手工构造两个历史会话文件，`/resume` 正确按新到旧列出、预览摘要准确、选号后 `agent.messages` 被替换、消息数回显正确；无历史会话时正确提示"没有可恢复的历史会话"
- ✅ 工具调用展示：用 `FakeMessagesAPI` 跑一轮"读文件→编辑文件→回复"的完整 `run_turn`，`⏺ read_file(...)` / `⎿ ...` / `edit_file` 的红绿 diff 均按预期渲染，回调链路（`on_tool_call` → 工具执行 → `on_tool_result`）在真实 `Agent` 循环里跑通，不是孤立单测

## 跟着学

1. `minicode/cli.py` 里 `_prompt_from_list` 和三个 `prompt_*_choice` 函数——看"三个相似交互命令怎么抽出一份共享逻辑，同时保留各自的选项内容"，这是"消除重复但不过度抽象"的一个小例子。
2. `minicode/agent.py` 的 `_execute_tool`/`_run_tool` 拆分——对比拆分前后的 diff，体会"多出口函数加一个统一回调"这类需求，为什么"先拆出单一出口"比"每个 return 前面塞一行"更不容易出错。
3. `minicode/session.py` 的 `list_sessions`/`load`/`load_latest` 关系——`load_latest` 现在是 `list_sessions` 的特例，观察"给已有能力再包一层"和"重新写一套"之间怎么选。

## 遗留问题 / 待确认

- **`cli.py` 已超过 300 行规定**（见"踩坑记录"），建议拆成 `cli.py` + `display.py` + `slash.py` 三个文件，职责边界已经清楚。这是本文档记录的这轮改动直接导致的，按红线应该先问再动手，目前还没做，等项目所有者确认要不要拆。
- Claude Code 真实的输入框是打字时会动态变形的圆角边框（Ink/React 撑起来的），本项目只用 `rich` + 内置 `input()` 做不到——这需要引入 `prompt_toolkit` 或 `textual` 这样的新依赖，按 CLAUDE.md 3.2 节"想加依赖先说明理由、停下来等确认"，目前维持只用 `rich` 的"神似"方案，没有引入。
- 子 agent（`task` 工具）的工具调用展示（`minicode/tools/task.py` 的 `on_subagent_tool_call`）还是原来的朴素 `print` 格式，没有跟着这轮一起换成 `⏺`/`⎿` 风格——它是独立模块、用原生 `print` 而不依赖 `cli.py` 的 `console`，这次没有触碰，风格上跟主 agent 的工具调用展示不一致。
