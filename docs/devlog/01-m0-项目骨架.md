# M0：项目骨架

日期：2026-07-08

## 做了什么

搭好整个项目能跑起来的最小骨架：`uv` 项目初始化、`minicode` 包的目录结构（含后续里程碑要用到的占位文件）、`config.py`（模型/常量配置）、`cli.py`（欢迎语入口）、一个冒烟测试，以及 git 仓库和首次提交。

新增文件：
- `pyproject.toml`（手写，而非 `uv init` 默认输出，原因见下）
- `minicode/__init__.py`、`config.py`、`agent.py`（占位）、`permissions.py`（占位）、`context.py`（占位）
- `minicode/tools/__init__.py`（占位）、`tools/base.py`（占位）
- `minicode/cli.py`
- `tests/test_cli.py`

## 关键设计决策

**1. 手写 `pyproject.toml`，放弃 `uv init --package` 的默认 `src/` 布局。**
`uv init --package` 默认生成 `src/minicode/` 的 src-layout，这是现代 Python 打包的推荐做法，但和 CLAUDE.md 里已经写死的扁平目录结构（`minicode/` 直接在项目根下）不一致。教学项目里"文档和代码要对得上"比"用最新最佳实践"更重要——初学者对着 roadmap 找文件时不该有额外的路径换算。构建后端也从 `uv_build` 换成了更通用、文档更多的 `hatchling`（`[tool.hatch.build.targets.wheel] packages = ["minicode"]` 即可支持扁平布局），这样将来读者查资料时不会被小众构建后端的文档卡住。

**2. 模型后端：DeepSeek 的 Anthropic 协议兼容端点，而非官方 Anthropic API。**
这是执行过程中和项目所有者确认后调整的（原计划用官方 Anthropic API）。DeepSeek 提供 `https://api.deepseek.com/anthropic` 端点，认证方式、`tools` 字段、`tool_choice` 都跟官方协议兼容，所以**代码层面完全不用变**——还是用官方 `anthropic` SDK，只是 `Anthropic(base_url=...)` 多传一个参数。这是本项目少有的"改了技术选型但零架构影响"的例子，也说明了当初选 Anthropic API 而不是自建 Provider 抽象层这个决定的价值：协议选对了，供应商可以换。

已知的能力差异记在了 `config.py` 顶部注释和 CLAUDE.md 3.2 节：不支持图片/文档内容、`cache_control` 等高级字段被忽略、**不支持 MCP 工具**（这条会在 M9d 时重新提起——我们自己手写的 MCP 客户端不依赖 DeepSeek 端支持，所以不受影响）。

**3. 模型档位映射（`TIER_MODELS`），而不是直接写死模型名字符串。**
项目所有者提出：既然 DeepSeek 官方本来就把 Claude Sonnet/Haiku → `deepseek-v4-flash`、Opus → `deepseek-v4-pro` 做了映射，不如顺势做成可切换的档位系统。所以 `config.py` 不暴露具体模型名，只暴露 `resolve_model(tier)`。这是个小设计但值得强调：**业务代码永远不应该在多处出现裸的模型名字符串**，换供应商/换模型时改一个地方即可。CLI 的 `--tier` 参数（M1 起）和运行时 `/model` 命令（M8）都基于这一层。

**4. 占位文件写"设计意图"而不是留空。**
`agent.py`、`permissions.py`、`context.py`、`tools/*.py` 现在都是空实现，但 docstring 里写了这个文件将来要做什么、对应哪个里程碑、核心设计思想的一句话摘要。这样即使读者现在只翻到 M0，打开这些空文件也能对整个架构有个预览，不会觉得"这是个没写完的烂摊子"。

## 踩坑记录

- `uv init --package` 和手写扁平布局的冲突：一开始直接跑了默认命令，产生了 `src/minicode/`，发现和文档不符后整个重来（删掉 `src/`、`.python-version`、`pyproject.toml`，改手写）。**教训**：涉及目录结构这种一旦写代码就难改的决策，脚手架命令的默认行为要先确认符不符合已经定好的规范，而不是先跑起来再看。
- `tests/` 目录一开始想留空（roadmap 原文允许"0 个测试也算通过"），但 `pytest` 在没有任何测试时退出码是 5（不是 0），会让"退出码 0"这条验收标准产生歧义。改成写一个真正有意义的冒烟测试（验证欢迎语内容），比放一个 `assert True` 占位测试更符合"测试要有实际意义"的精神，也让退出码确定性地是 0。

## 跟着学

1. 先看 `docs/01-architecture.md` 第 1、2 节，对整个架构有个全局印象，再回来看代码目录——这样打开每个占位文件时，会知道它在架构图里对应哪一层。
2. `minicode/config.py`：重点看 `resolve_model()` 这几行。这是本项目里"配置与业务代码解耦"的一个小例子，之后所有涉及模型调用的地方都会调这个函数而不是硬编码模型名。
3. 对照 `pyproject.toml` 和 `minicode/cli.py`，理解 `[project.scripts]` 是怎么把 `minicode = "minicode.cli:main"` 变成 `uv run minicode` 这个命令的——这是 Python 打包里"入口点（entry point）"机制，之后不会再展开讲，这里顺带认识一下。
