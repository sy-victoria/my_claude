# M6：上下文管理

日期：2026-07-13

## 做了什么

解决长对话的核心工程问题：上下文窗口是稀缺资源。三个手段全部落地——token 用量跟踪（API usage 字段）、自动/手动 compaction（把旧历史总结成摘要替换掉）、read_file 分页（offset/limit）。

新增/修改：`minicode/context.py`（ContextTracker + 切分/合并纯函数）、`agent.py`（轮次开始时检查压缩、`compact()` 方法、usage 记录）、`tools/read_file.py`（分页）、`cli.py`（token 显示 + `/compact` 命令雏形）、`config.py`（窗口/阈值/读取行数常量）、`tests/test_context.py`（9 个测试）。

## 关键设计决策

**1. compaction 在轮次边界触发，不在轮次中间。**
`run_turn` 开头检查 `should_compact()`——此刻 messages 一定以完整的 assistant 回复结尾。如果在工具调用循环中间压缩，可能把 tool_use / tool_result 对拆开（两者必须成对，拆开 API 直接报错）。切分点同理：选**最后一条真实用户输入**（content 是字符串的 user 消息；tool_result 的 content 是列表，天然不会被选中）。

**2. 摘要并入保留部分的第一条用户消息，不单独插一条。**
避免出现两条相邻 user 消息，维持角色交替的合法结构。`merge_summary()` 是纯函数，测试直接断言结构。

**3. 摘要指令明确"保留什么、丢什么"。**
保留：任务目标、已做决定、文件清单、当前进度。丢弃：工具返回的原始文件内容和命令输出——**需要时可以重新读，文件系统本身就是 coding agent 的外部记忆**。验收里模型完美演示了这一点：压缩后被问函数数量，它不依赖摘要里的模糊记忆，直接 grep 重新数了一遍。

**4. 上下文体积用 `usage` 字段近似，不自己数 token。**
每次响应的输入 token 数 ≈ 当前对话历史体积，官方计数免费送，没必要引入 tokenizer 依赖。

## 踩坑记录（本里程碑最有价值的一段）

**第一次真实验收 compaction 根本没触发。** 现象：连续读了两个 900 行的文件，`usage.input_tokens` 却越来越小（轮次 3 只有 75）。排查后发现：DeepSeek 的兼容端点默认开启 prompt 缓存，**命中缓存的输入 token 被从 `input_tokens` 里拆出去，单独报在 `cache_read_input_tokens` 里**。我们只看 `input_tokens`，于是长对话里"上下文体积"读数反而下降，阈值永远够不着。

修复：`ContextTracker.record()` 把 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` 三者加总。修复后重跑：轮次 3 开始时正确触发压缩（16 条消息 → 4 条，15k → 3.6k tokens）。

教训：**usage 字段的语义在不同后端/开启缓存后会变化，"上下文有多大"和"这次请求计费多少 token"是两个不同的问题。** 这个坑在任何接过缓存的 LLM 应用里都会出现，值得记住。

## 验收结果

- ✅ `uv run pytest` 64 个全绿
- ✅ 真实验收（阈值人为调低到 3.8k tokens）：读两个 900 行文件推高上下文 → 轮次 3 开始时自动 compaction（16 → 4 条消息，日志可见）→ 压缩后继续对话正常
- ✅ 压缩后问"最初的总任务是什么、输出到哪个文件"→ 准确答出"写 API 文档、API_DOC.md"（信息来自摘要）
- ✅ 每轮 CLI 显示 token 用量；`/compact` 手动触发可用
- ✅ 意外收获：模型自发用 offset=500 分页读完 900 行文件（分页提示文案在起作用）

## 跟着学

1. `minicode/context.py` 的 `split_for_compaction()` + `merge_summary()`——compaction 的全部结构性逻辑就这两个纯函数，先读注释再读代码，思考"为什么切分点必须是真实用户输入"。
2. `context.py` 里 `record()` 的缓存踩坑注释 + 本文踩坑记录——面试聊到 prompt caching 时这是个很好的一手案例。
3. `SUMMARY_INSTRUCTION` 的措辞——对比验收轮次 4 的回答，看摘要指令里"必须保留任务目标"这一条是怎么变成模型行为的。

## 遗留问题

- compaction 用主模型总结，成本略高（Claude Code 用便宜的小模型干这活）；单模型约束下接受。
- 压缩后 `_read_files` 集合没有清空——摘要里说"读过 X 文件"但原文已丢，编辑约束仍放行。风险很低（模型通常会重读），记录在案。
